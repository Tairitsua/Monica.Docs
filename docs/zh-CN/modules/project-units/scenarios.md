# 接入场景

## 新功能

1. 确认所属子域和负责团队。
2. 实现前先确定稳定需求 ID。
3. 为功能中的每个被发现单元添加元数据和需求注解。
4. 构建宿主并打开“状态概览”。
5. 打开缺口行，检查描述、依赖、方法、告警和需求链接。

标题应描述单个单元，而不是所有类型重复同一个功能名。例如，请求、应用服务和领域服务可以分别命名为“审核订单命令”“审核订单”和“订单审核规则”。

## 现有服务

先启用发现和命名警告。初始面板可能显示 0% 元数据和需求覆盖率，这是有效基线，不是启动错误。

建议按以下顺序处理：

1. 错误和格式不正确的明确注解。
2. 公共应用边界和高依赖单元。
3. 负责人缺口。
4. 需求追踪缺口。
5. 其余描述和标签。

不要为了提高百分比而编造需求 ID。无法确认的追踪关系应保持可见缺口，直到找到真实来源。

## 多服务

每个服务只报告自己的目录和 `IMonicaApplicationOptions` 身份。网关可以聚合 `/framework/units/dashboard` 快照，但 Monica 不会在单个服务宿主内部合并跨服务目录。

## 集成需求系统

文档存储位置或路由变化时，应保持需求注解稳定，只更新宿主的 `IProjectUnitRequirementLinkResolver`。这样可以把持久追踪关系与界面导航解耦。

## Agent 工作方式

Agent 添加注解前应先读取仓库事实；负责人或需求身份存在歧义时应询问用户；四项覆盖率必须分别处理。状态面板只能证明目录上下文的完整程度，不能证明业务实现正确。
